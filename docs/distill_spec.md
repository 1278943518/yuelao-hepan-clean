# 相亲博主语料蒸馏规范 v2

> 目标：把每条视频的口播转写稿压缩成一条**结构化记录**。
> v1 只抓「案例型」（某人自述条件+博主判断），实测只覆盖约 1/9 的视频；
> **v2 增加「观点型」抓取**——博主的主张、论断、方法论才是规则库的主要来源。

## 输入 / 输出

- 输入：`data/transcripts/{aweme_id}.json`（字段 `subtitle_text` 口播全文、`desc`、`duration`）
- 批次：`data/batches/batch_XX.txt`
- 输出：`data/distilled/{aweme_id}.json`（一条视频一个文件）

## 输出 Schema（v2）

```json
{
  "aweme_id": "7675300412546698531",
  "blogger": "B",
  "desc": "别拿你这点认知来挑战饭碗",
  "duration_s": 96,

  "has_case": false,
  "has_claim": true,
  "content_type": "反驳质疑",

  "speaker_gender": null,
  "case_summary": null,
  "self_attrs": null,
  "self_level": null,
  "demand": null,
  "demand_gates": [],
  "verdict": null,
  "verdict_quote": null,
  "reasons": [],
  "flaws": [],
  "advice_given": null,

  "core_claims": [
    "有人质疑博主靠压低对方配得感赚钱",
    "博主否认存在金钱利益关系",
    "给客户画像时故意只给 60 分档，因为给高了预期只会更高"
  ],
  "rules": [
    { "when": "给客户做择偶定位", "then": "只给到 50-60 分的画像区间，压低预期", "basis": "画像给高会抬高客户预期" }
  ],
  "key_concepts": ["配得感", "画像", "预期管理"],
  "stance_on_market": "对对碰市场里，价格由自身价值决定；给高画像等于害人",
  "market_mechanism": ["压价", "预期管理"],

  "hooks": ["择偶定位咨询（收费）"],
  "confidence": "high"
}
```

## 字段规则

### 通用
| 字段 | 规则 |
|---|---|
| `blogger` | `A` = 苏锡常大王说媒；`B` = 苏州金大王；`C` = 天书定位（9月19来南京）；`D`… 后续顺延 |
| `content_type` | 从以下选一：`案例点评` / `择偶定位方法论` / `价值互换论` / `性别差异论` / `反驳质疑` / `服务介绍` / `现场花絮` / `无口播内容` |
| `has_case` | 是否存在「某人自述条件 + 博主给出判断」的完整案例 |
| `has_claim` | 是否有明确的观点主张（几乎全部视频都应为 true） |
| `core_claims` | 博主的核心主张，3-6 条，每条 ≤30 字，**按视频里的叙述顺序** |
| `rules` | 可计算的判断规则，0-4 条。`when` = 触发条件，`then` = 博主的结论/建议，`basis` = 博主给的理由。这是规则库的直接来源 |
| `key_concepts` | 博主反复使用的概念词，如「配得感」「画像」「价值互换」「对对碰市场」「门当户对」「上迁婚」 |
| `stance_on_market` | ≤50 字，博主对婚恋市场**性质**的判断（是价值互换？是对价市场？是概率问题？） |
| `market_mechanism` | 博主话语中体现的市场机制词，可选：`压价` / `抬价` / `预期管理` / `价值互换` / `信息不对称` / `画像匹配` / `梯度择偶` / `概率筛选` |
| `hooks` | 导流转化钩子，如「加微信咨询」「择偶定位收费」「招销售」；没有则 `[]` |
| `confidence` | 转写质量与抽取把握：`high` / `mid` / `low` |
| `notes` | 可选，≤40 字，记录特殊情况 |

### 案例型（`has_case = true` 时必填）
| 字段 | 规则 |
|---|---|
| `speaker_gender` | 自述方性别 `M`/`F`，无法判断填 `null` |
| `case_summary` | 一句话 ≤80 字 |
| `self_attrs` | 自述方条件，缺失填 `null` |
| `self_level` | 综合条件档次：`低`/`中`/`高`（用于条件弹性检验） |
| `demand` | 对对方的要求 |
| `demand_gates` | 博主明确说「必须」「不能接受」「卡死」的项 |
| `verdict` | 归一化为：`追不到` / `偏难` / `需降低标准` / `可以` / `看情况` / `未给出` |
| `verdict_quote` | 支撑结论的原文短句 ≤30 字 |
| `reasons` | 博主给的理由，每条 ≤20 字 |
| `flaws` | 博主点出的**短板**，每条 ≤12 字（如「身高要求过窄」「年龄偏大」） |
| `advice_given` | 博主给的调整建议 |

## 转写噪声处理（必做）

Whisper 自动识别存在**同音字错误**，需按上下文纠正后再抽取：

| 转写错字 | 实际含义 |
|---|---|
| 大战毕业 | 大专毕业 |
| 书康行业 / 数空 | 数控行业 |
| 礼仪 | 离异 |
| 养肉 / 江这户 | 苏北（方言）/ 江浙沪 |
| 喀 | 卡（卡条件） |
| 责偶定位 / 则偶 | 择偶定位 |
| 配德感 | 配得感 |
| 画像（上下文指代" рекоменд 给客户的择偶建议档次"） | 保留，这是行话 |
| 对对碰市场 | 保留，这是行话（指相亲配对市场，区别于自由恋爱） |
| 洗藏办 | 洗脚店？按上下文忽略 |

数字若明显矛盾，取语义更合理者，并把 `confidence` 标 `mid`。

## 效率要求（省 token，必须遵守）

1. **一次只读一条**转写稿 → 立刻写该条 JSON → 再读下一条。不要把整批读进上下文。
2. 每条记录 30-50 行 JSON，不复述原文，不输出分析过程。
3. `core_claims` 每条 ≤30 字；`rules` 每条不超过 3 个字段。
4. JSON 必须能被 `json.load` 解析（UTF-8，无注释、无尾逗号）。
5. 全部处理完只回报一行统计。

## 回报格式

`batch_XX 完成 N 条 | 案例型 X 条 | 观点型 Y 条 | 男自述 a / 女自述 b | 追不到 c | 偏难 d | 需降低标准 e`
